# Decisions

**History and memory are different things, in different tables.** `messages` is an append-only record of what was said, including attached documents. `memory_items` and `memory_versions` hold only what the user explicitly chose to keep. Nothing reads history to infer memory, and deleting a memory item does not rewrite history. History is passed to the model as conversation context; memory is read through a tool so every read is logged.

**Writes need a user action. The model has no write tool.** Memory changes in exactly two ways: the user calls the memory API (`POST`, `PATCH`, `DELETE /memories`), or the user's own chat message starts with `/remember` or `/forget`. The server parses that command before any model runs. Attached documents and model output are never parsed for commands. The model gets `read_memory` and `get_orders_report` only, so a model fooled by a document has nothing to call: the test with a deliberately gullible scripted model shows its write attempts coming back as `UNKNOWN_TOOL`. Natural-language "remember that..." in chat is not acted on either; that would need intent detection, which is exactly the kind of judgement a document can manipulate.

**Owner comes from the token only.** The token is HMAC-SHA256 signed and carries the user id. Request bodies are strict zod schemas and any field that tries to name a user (`owner`, `user_id`, `userId`, `sub`, ...) is rejected with `400 IDENTITY_IN_BODY` rather than silently ignored, so a client bug is loud. Query strings are never read. Every `MemoryStore` and `HistoryStore` method takes the owner as its first argument and every query filters on it, so even code inside the server cannot fetch an item without saying whose it is. The `read_memory` tool is built per request with the owner bound in a closure; the model cannot pass one.

**404, not 403, for another user's item.** Bob asking for Alice's item gets exactly the same response as asking for an id that does not exist: `404 NOT_FOUND`, "no memory item X for this user". A 403 would confirm the id exists and belongs to someone, which lets ids be probed. The server log still records each attempt as `access_denied_or_missing` with the caller and target, so the attempt is visible to an operator.

**Soft history on correction, value erasure on delete.** A correction adds a new version and marks the old one superseded, so the user can see what changed and from which source (message id or request id). A delete is different: the user wants the value gone. The item keeps a tombstone (key, timestamps, delete source) for audit, but every stored value, including superseded ones, is set to NULL. The same key can be saved again later as a fresh item. A partial unique index keeps at most one live item per owner and key.

**Test authentication, clearly labelled.** Two seeded users with published passwords, scrypt password hashes, HMAC tokens with a one-hour expiry. The signing secret is random per process, so tokens die on restart and the restart test has to log in again (and checks that the old token is refused). This is enough to prove the backend decides identity. It is not production auth: no refresh, revocation, rate limiting, CSRF handling or password reset.

**`node:sqlite`, one file, a real second process.** Built-in `DatabaseSync`, no native dependency to compile. WAL mode, foreign keys on. The restart test and the demo spawn `src/cli/serve.ts` as a separate OS process twice against the same file, so persistence is proven across a process boundary, not just across two connections in one process. `node:sqlite` still prints an ExperimentalWarning on Node 22, so the npm scripts pass `--disable-warning=ExperimentalWarning`; it needs Node 22.13 or later.

**Known keys are strict.** `language` (en, sv, fr) and `report_format` (bullets, table) are enums, normalised for case. Other keys are allowed as short snake_case text, so the store is not tied to two preferences, but the assistant only acts on the two it knows.

**Reused from agent-toolkit, copied not imported.** `registry.ts`, `errors.ts`, `log.ts` and `model/*` are copies from agent-toolkit rev 5ea765f, with the log formatter extended for memory events. Each repo has to run on its own; a shared versioned package can come with agent-api-sdk.

**Grounding check on memory ids.** The final answer must list which memory items shaped it, and each id must have come back from `read_memory` in this run. Like agent-toolkit's evidence check, it catches citing something never read. It does not prove the text really follows the preference; that is a model-quality question for agent-evals.

**Not done on purpose.** No natural-language memory extraction, no memory suggestions the user confirms, no embeddings, no per-item sharing between users, no encryption at rest. Each is a reasonable next step and none changes what this project has to prove.
